# PBI バックログと設計ゲートの導入 — タスク分解の 3 層化・Phase 1 承認ゲート・1 PBI = 1 ファイル再編

## 背景・目的

- 従来のワークフローはタスクと PR の 2 粒度で、PR の切れ目 (垂直スライス) を Phase 3 で発見的に判断していたため、集約タイミングが実装後の裁量に依存していた。
- 本 PR で PBI (Product Backlog Item) 層を導入して垂直スライスの計画を設計時に確定し (1 PBI = 1 PR)、その計画をユーザーが実装開始前に承認する設計ゲートを Phase 1 に新設した。
- タスク分解の物理形式も 1 PBI = 1 ファイルの `docs/tasks/<work-name>/` ディレクトリに再編し、下流エージェントの参照をすべて追随させた。

## スコープ

- 次の Path C セッションから「仕様 + PBI バックログのユーザー承認 → PBI 単位の実装 → PBI 完了時の出荷」という新しい流れで実際に運用できるようにした。
- タスク分解に PBI 層を導入し、1 PBI = 1 PR とした。
- Phase 1 に常時ブロッキングの設計ゲートを新設した。
- タスク分解を 1 PBI = 1 ファイル構成に再編した。

## 受け入れ基準

このリポジトリにタスク分解文書はないため、集約対象の変更一覧をグルーピングの基準とする。

### タスク分解に PBI 層を導入し、1 PBI = 1 PR とした

- 成果物を「仕様書 = 何を約束するか / PBI = 動作確認可能な垂直スライス (スライス文 + スライスレベル受け入れ基準) / タスク = TDD 1 サイクルの原子的作業」の 3 層に再定義した。
- 全タスクはちょうど 1 つの PBI に属する。
- Phase 3 の集約トリガーを発見的判断 (〜5 タスク到達等) から「PBI 配下の全タスクが fix loop を抜け、スライスレベル受け入れ基準が実行中のシステムで動作確認可能」に変更した。
- 機能全体の完了定義を「全 PBI が出荷され、各スライス AC が実機で確認済み」に変更した。
- スライス計画が崩れた場合は `architect` に差し戻して再スライスし、改訂バックログは設計ゲートを再通過する。
- タスク表に「対応する仕様」列を追加し、各タスクが実現する仕様の振る舞い (ユースケース名等) を明示した。
- PR 文書の受け入れ基準は PBI のスライス AC を先頭の `###` グループに置く形式とし、`pr-style.md` の Severity Matrix に 🟡 項目を 1 件追加した。

### Phase 1 に常時ブロッキングの設計ゲートを新設した

- 旧 Task Plan Report (`architect` が曖昧さをフラグした場合のみ停止) を廃止し、ユーザーの明示承認を Phase 2 開始の必須条件に変更した。
- ゲート報告は「仕様更新の一覧 / 出荷順の PBI 一覧 (スライス AC + タスク) / 仕様カバレッジ対応表 (実現タスクのない仕様・仕様アンカーのないタスクを明示) / 曖昧さフラグ」を含む。
- Definition of Done 1a を「設計ゲート通過 (事前のユーザー承認)」に変更した。
- Path C のユーザーゲートは設計ゲートと集約ハンドオフの 2 点に確定した。

### タスク分解を 1 PBI = 1 ファイル構成に再編した

- `docs/tasks/<work-name>.md` 単一ファイルを廃止し、`docs/tasks/<work-name>/` ディレクトリ (日本語 README バックログ索引 + `<N>-<pbi-slug>.md`、`<N>` は出荷順で PR 連番と通常一致) に変更した。
- PBI ファイルは `# PBI: <スライス文>` タイトル + 受け入れ基準 + タスク分解表で構成する。
- 「README everywhere」規約に `docs/tasks/<work-name>/` を追加した。
- 下流参照 (5 エージェント定義 + `pr-style.md` / `spec-style.md`) をすべて PBI ファイル参照に更新し、旧形式参照の残存ゼロを確認した。

## 変更内容

開発の成果物を仕様書 / PBI / タスクの 3 層に再定義し、垂直スライスの計画確定を実装後の裁量から設計時のユーザー承認事項に移した。

### PBI 層の導入と 1 PBI = 1 PR 化

- タスク分解を「PBI に分割 → 各 PBI をタスクに分割」の 2 段階に再定義した (`CLAUDE.md` 「Task Decomposition」、`agents/architect.md` 「Task Decomposition」)。
- PBI の性質を明文化した。
  - スライス文はユーザーが観測できる 1 文の成果で命名する (レイヤー名・コンポーネント名は不可)。
  - スライスレベル受け入れ基準は、実行中のシステムでコンポジションルート経由で動作確認できる振る舞いとする。
  - 出荷順に並べ、最初の PBI は入力から観測可能な出力までの最薄経路とする。
  - 〜5 タスクまたは〜2 関心事を超えたら分割する。
- タスク表に「対応する仕様」列を追加し、各タスクが実現する仕様の振る舞いを明示して設計ゲートでの仕様カバレッジ照合を可能にした。
- Phase 3 の集約判断を設計時計画 (PBI) ベースに置き換えた。
  - 集約トリガーは「PBI の全タスク完了 + スライス AC の動作確認可能 + reconcile 済みでグリーン」の 3 条件。
  - スライス計画が崩れた場合は `architect` に差し戻して再スライスし、改訂バックログは設計ゲートを再通過する。
  - 機能全体の完了を「全 PBI 出荷 + 各スライス AC の実機確認」に変更した。
- PR 文書の受け入れ基準に PBI 先頭グループを導入した。
  - 先頭 `###` グループの見出しをスライス文、本文をスライスレベル受け入れ基準とする。
  - 先頭 PBI グループを欠く場合の 🟡 行を Severity Matrix に追加した。
  - 対象: ルール `rules/pr-style.md`、エージェント定義 `agents/pr-writer.md` / `agents/pr-reviewer.md`。

### 設計ゲートの新設 (Phase 1)

- 実装開始前の方向合わせとして、ユーザーの明示承認を必須とするゲートを Phase 1 step 2 に置いた (`CLAUDE.md` 「Orchestration Loop」)。
  - 旧 Task Plan Report (曖昧さフラグ時のみ停止) を廃止した。
  - ゲート報告は仕様更新の一覧・出荷順の PBI 一覧・仕様カバレッジ対応表・曖昧さフラグで構成する。
  - 曖昧さフラグの役割を「停止のトリガー」から「レビューの注目点の指示」に変更した (ゲートは常に停止する)。
- `architect` のハンドオフ報告を設計ゲート向けに書き換えた (`agents/architect.md` 「Report for the Design Gate and Hand Off」)。
- 完了条件とユーザー相談ポイントをゲート前提に更新した (`CLAUDE.md`)。
  - Definition of Done 1a を「設計ゲート通過 (事前のユーザー承認)」に変更した。
  - ユーザー相談ポイントを設計ゲート / 集約ハンドオフ / PBI 再スライス / 依存承認 / 曖昧要件 / 非収束エスカレーションに整理した。

### タスク分解の 1 PBI = 1 ファイル再編

- タスク分解の置き場を単一ファイルからディレクトリに変更した (`docs/tasks/<work-name>/`)。
  - 日本語 README がバックログ索引 (作業が届けるもの + 出荷順の PBI 一覧) を担う。
  - PBI ファイル (`<N>-<pbi-slug>.md`) は `# PBI: <スライス文>` タイトル + スライスレベル受け入れ基準 + タスク分解表で構成する。
- ディレクトリレイアウト図と「README everywhere」規約を新構成に更新した (`CLAUDE.md`)。
- 下流エージェントとルールの参照先をすべて PBI ファイル形式に追随させた。
  - エージェント定義: `agents/developer.md` / `agents/code-reviewer.md` / `agents/pr-writer.md` / `agents/pr-reviewer.md`。
  - ルール: `rules/pr-style.md` / `rules/spec-style.md`。

## 影響範囲・注意点

### 有効化タイミング

- 変更は次セッションから有効になる (`CLAUDE.md`・エージェント定義・ルールはセッション起動時に読み込まれる)。

### ワークフローの体感変化

- Path C の着手前に必ず設計ゲートの承認待ちが挟まる (従来は `architect` が曖昧さをフラグした場合のみ停止)。
- 集約タイミングの裁量判断 (〜5 タスク到達等の発見的トリガー) は廃止され、PBI 完了が集約の基本トリガーになる (ユーザーの出荷指示時は PBI を切り直して閉じる)。

### 本 PR 自体の逸脱事項

- 本 PR 文書は仕様書も PBI ファイルもないリポジトリで作成しており、受け入れ基準は先頭 PBI グループなしの変更一覧ベースで構成している (新設した 🟡 行の対象外)。

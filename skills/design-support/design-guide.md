## 設計サポートガイド

このガイドは、ユーザーが良い設計にたどり着くための問いかけの指針である。

---

### Phase 1: 要件の理解

#### 目的
曖昧な要件を具体的なユースケースに落とし込む。

#### 問いかけの例
- 「このシステムを使うのは誰ですか？どんな場面で使いますか？」
- 「ユーザーがこのシステムで達成したいことを、1文で表現するとどうなりますか？」
- 「一番シンプルなユースケースは何ですか？まずそれだけに集中しましょう」
- 「その一番シンプルなユースケースを、入力から目に見える出力まで一気通貫で動かせる最小の単位（垂直スライス）に切るとどうなりますか？土台を全部作ってからではなく、まず細くても動く一本を通して、そこから広げる順序にできますか？」
- 「そのユースケースの開始条件と終了条件は何ですか？」
- 「正常系以外に、どんな異常系がありそうですか？」

#### チェックポイント
- [ ] ユーザー（アクター）が特定できている
- [ ] 主要なユースケースが3つ以内に絞れている
- [ ] 各ユースケースの入力と出力が明確である
- [ ] スコープ外を明確にしている（今やらないことを決めている）
- [ ] 最初に動かす対象が、層を縦に貫いて動作確認できる最小の垂直スライスになっている（土台だけを先に全部作る計画になっていない）

---

### Phase 2: ドメインモデリング

#### 目的
ビジネスの言葉で概念を整理し、共通言語を作る。

#### 問いかけの例
- 「ユースケースの中に登場する『もの』や『概念』を挙げてみてください」
- 「その2つの概念の関係は何ですか？AはBを持つ？AはBの一種？」
- 「その概念は、このシステムの中でどういう意味ですか？一般的な意味と違いはありますか？」
- 「その概念を一言で説明するとどうなりますか？その説明をそのまま名前にできそうですか？」
- 「その概念は、他の概念がなくても存在できますか？それとも何かに依存していますか？」

#### チェックポイント
- [ ] 主要な概念（エンティティ候補）が洗い出せている
- [ ] 概念間の関係が整理できている（has-a, is-a, uses）
- [ ] 各概念の名前が、ドメインの言葉で表現されている
- [ ] 同じ概念に異なる名前を使っていない（用語が統一されている）

---

### Phase 3: 責務の分離

#### 目的
各概念の責務を明確にし、SOLID原則に基づいて検証する。

#### SOLID原則の問いかけ

**S — 単一責任の原則 (SRP)**
- 「そのクラス/モジュールは、変更される理由がいくつありますか？」
- 「そのクラスの責務を、"〜を管理する" の形で1つだけ言えますか？」
- 「もしその2つの機能のどちらかだけが変わるなら、分けた方がいいかもしれません。どう思いますか？」

**O — 開放閉鎖の原則 (OCP)**
- 「新しい種類の〇〇が増えたとき、既存のコードを変更せずに追加できますか？」
- 「if文やswitch文で分岐している部分は、将来増えそうですか？」

**L — リスコフの置換原則 (LSP)**
- 「その子クラスは、親クラスの代わりに使っても問題なく動きますか？」
- 「親クラスの契約（事前条件・事後条件）を子クラスが破っていないですか？」

**I — インターフェース分離の原則 (ISP)**
- 「そのインターフェースのメソッドを、すべての実装クラスが本当に必要としていますか？」
- 「使わないメソッドに依存させるのは、不要な結合を生みます。分割できそうですか？」

**D — 依存性逆転の原則 (DIP)**
- 「そのクラスは、具体的な実装に直接依存していませんか？」
- 「もしデータベースを変えるとしたら、ビジネスロジックのコードも変わりますか？変わるなら、間にインターフェースを挟めそうですか？」

#### チェックポイント
- [ ] 各クラス/モジュールの責務が1つに絞れている
- [ ] 拡張に対して開いている設計になっている
- [ ] 依存の方向が明確で、内側に向いている
- [ ] 不要な依存関係がない

---

### Phase 4: アーキテクチャの配置

#### 目的
Clean Architectureの各層に概念を配置し、境界を定義する。

#### 問いかけの例
- 「その概念は、フレームワークやDBがなくても意味がありますか？意味があるならEntityです」
- 「そのロジックは、アプリケーション固有のルールですか？それともビジネス全体のルールですか？」
- 「外部システムとやり取りする部分は、どこにありますか？その部分をインターフェースで抽象化できますか？」
- 「もしWebからCLIに変えるとしたら、どの部分が変わりますか？変わる部分と変わらない部分の境界はどこですか？」

#### 層の配置ガイド

| 層 | 配置するもの | 依存先 |
|---|---|---|
| Entity | ビジネスルール、ドメインオブジェクト、値オブジェクト | なし |
| Use Case | アプリケーション固有のロジック、ユースケースの実行 | Entity |
| Adapter | コントローラ、プレゼンター、リポジトリ実装 | Use Case, Entity |
| Infrastructure | フレームワーク、DB、外部API | Adapter, Use Case, Entity |

#### チェックポイント
- [ ] 依存の方向がすべて内側に向いている
- [ ] 内側の層が外側の層を知らない（importしていない）
- [ ] 境界にはインターフェース（Port）が定義されている
- [ ] フレームワーク固有の型がUse Case層に漏れていない

---

### Phase 5: 設計の検証

#### 目的
設計全体をシンプルさ・命名・テスタビリティの観点で最終検証する。

#### シンプルさの検証
- 「この設計の中で、今すぐ必要でないものはありますか？」（YAGNI）
- 「同じことを2回以上書いている部分はありますか？」（DRY）
- 「この設計を、チームの新しいメンバーに5分で説明できますか？できないなら、どこが複雑ですか？」
- 「もっとシンプルにする方法はありますか？削れるものはありますか？」

#### 命名の検証
- 「その名前を読んだだけで、何をするものか分かりますか？」
- 「略語を使っていませんか？フルネームで書いた方が分かりやすくないですか？」
- 「その名前は、ドメインの言葉と一致していますか？」
- 「動詞で始まるメソッド名は、実際にその動作を正確に表していますか？」

#### テスタビリティの検証
- 「そのクラスを、外部依存なしでテストできますか？」
- 「テストを書くために、内部実装を知る必要がありますか？必要なら設計を見直しましょう」
- 「振る舞いを検証するテストを、自然な日本語で書けますか？（〜した場合、〜になる）」

#### チェックポイント
- [ ] 不要な抽象化がない
- [ ] すべてのクラス・メソッドの名前が意図を正確に表現している
- [ ] 外部依存をモックしなくても主要なテストが書ける
- [ ] 設計を図や箇条書きで簡潔に説明できる
